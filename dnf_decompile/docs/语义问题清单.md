> 优先级：**先确保语义正确，再追求 identical**。
> 本清单记录经 ORIG/NEW 反汇编对比确认的**未正确实现 / 语义问题**，不含仅偏移差（布局问题见各 class 报告）。
> 生成工具：`source/toolchain/scan_stubs.py`（桩检测）、`scan_semantic.py`（签名/参数不匹配）、`diff_func.py`（单函数对比）。

## 一、桩函数覆盖真实逻辑（最大类别，1191 个）`[Verified]`

检测规则：NEW 指令数 ≤12 而 ORIG ≥20 且 ORIG ≥2×NEW → NEW 为桩/空实现。当前二进制共 **1191** 个此类函数。

### 典型高价值桩（ORIG 指令数 → NEW 指令数）
| 函数 | ORIG→NEW | 位置 |
|---|---|---|
| `CDispatchServerPacket::dispatchPacket` | 6348→12 | Dispatcher 主分发 |
| `CUser::make_basic_info` | 2149→7 | 角色基本信息打包 |
| `Dispatcher_GM_Command::dispatch_sig` | 2058→5 | GM 命令分发 |

| 大量 `Dispatcher_*::dispatch_sig/process` | 400–1000→5 | 各协议包处理器 |

### 根因
这些桩定义在 `GameStubs.cpp`（CMakeLists L219 已编译链接），应替换为对应真实 TU 实现。多数因**头文件布局/重复符号/命名空间冲突**被阻挡暂未接入（见 README 批次说明）。

### 修复优先级建议
1. 先接 `CUser` 高频方法（AddItem/UpdateData/SetCharacLevel/log_out/giveup_panalty 等），影响面最大。
2. 再处理 `CInventory`、`CDungeon` 核心方法。
3. `Dispatcher_*` 包处理器体量大，按协议域分批。

## 二、签名 / 参数语义不匹配 `[Verified]`

检测信号：ORIG 与 NEW 的 `ret $N`（参数清理）或参数指针(0xc+ %ebp)解引用不同。

| 函数 | 问题 |
|---|---|
| `CUser::get_growth_power_exp_reward` | ORIG 从**第2参指针**读 0x8d24d 并写回首参（`ret $0x4` 清1参）；NEW 只从 `this` 读 0x8d250，忽略第2参。见 `CUser/问题点记录.md` §3。|
| `CInventory::GetInvenSlot` | ORIG `ret $0x4`（清参），NEW 无。签名/清理不一致。|

## 三、语义明确的单个 bug `[Verified]`
