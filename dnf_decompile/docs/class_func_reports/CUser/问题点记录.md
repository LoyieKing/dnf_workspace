# CUser 冲突问题点记录（2026-08-21 审计）

> 本文件记录 CUser 重构中经反汇编对比确认的**布局 / 语义**问题点。
> 结论标注来源：`[Verified]` 已从 ORIG/NEW 反汇编确认；`[Inferred]` 反编译/DWARF 推断。
> 修复原则：先确保**语义正确**，再追求 identical；涉及删除/移动字段需先确认不破坏已 identical 的访问。

## 1. CUser 整体 +4 布局错位（多个独立小错位叠加）

| `Character::m_schoolNo`(GetSchoolNo/SetSchoolNo) | 0x8e07c | 0x8e080 | +4 |
| `IsRecvEvent`(m_mcap 内) | 0x8e408 | 0x8e40c | +4 |

| `GetPICSMap`(m_map8eabc) | 0x8eabc | 0x8eac0 | +4 |

### 关键排除（避免误删）
- `CNetwork<4096,450000>` 自身 getter（`get_ip`/`get_port`/`get_mtu`/`get_nat_type`）**identical**，排除 CNetwork 尺寸问题。`[Verified]`
- `CUserCharacInfo` 基类 `m_selected`(0x10)/`m_tag`(0x14) 已确认正确（setCurCharac/setTagCharac identical）。`[Verified]`
- `getUsedCera`(0x8d0e0)、`GetMailBox`(0x71ad8)、`GetPVPRoom`(0x8d006) 等 0x8d0e0 前字段**正确**。
- `CSecurityCard`(0x4c)、`CPad`(0x48)、`CharacAdvanceAltarManager`(0xd4)、`CActionPointManager`(0xcfc)、`CerashopAddRestrict::UserInfo`(0x69) 尺寸注释链到 m_character=0x8e034 自洽。

**结论**：+4 非单一缺块，位于 0x8d0e4..0x8e07c 区间（m_levelupEvents/m_securityCard/m_cpad/m_379/m_lookOuts/m_ipCounters/m_ceraUserInfo/m_expReward/m_actionPoint/m_advanceAltar/m_character 之一），且与下述 STExpReward +3 叠加。**不安全的整体删除点，勿盲改。**

## 3. `get_growth_power_exp_reward` 语义/签名 bug `[Verified]`

`_ZN5CUser27get_growth_power_exp_rewardEv`（CUser.cpp:1217 `return m_expReward.m_reward;`）：

- ORIG：`mov 0xc(%ebp),%edx; mov 0x8d24d(%edx),%edx; mov %edx,(%eax)` —— 从**第 2 个参数指针**读 0x8d24d，再写回首个参数。
- NEW：`mov 0x8d250(%eax),%eax` —— 从 `this` 读 0x8d250，忽略第 2 参。

**结论**：ORIG 与 NEW 结构不同（NEW 未使用第 2 参，ORIG 从第 2 参指针读取）。`[Verified]` 需确认 ORIG 真实签名/语义（可能为 `int CUser::get_growth_power_exp_reward(CUser* other)` 或读取 `other->m_expReward.m_reward`），并核对函数名 mangling `Ev`（无参）与 ORIG 使用 0xc(%ebp) 的矛盾。

## 4. SetPowerUp / isHangameUser / setHangameUser 偏移 +3 `[Verified]`

- `SetPowerUp`：ORIG 写 0x8d253，NEW 写 0x8d256（+3）。
- `isHangameUser` / `setHangameUser`：ORIG 0x8d260，NEW 0x8d263（+3）。

与 STExpReward 内部错位同源（见 §2）。修复 STExpReward 布局可一并修正。

## 5. m_ceraUserInfo / std::map 尺寸存疑 `[Inferred]`

- `CerashopAddRestrict::UserInfo` 含 4 个 `std::map`（m_accountDaily/m_characDaily/m_field30/m_field48）+ 尾部 0x9 字节，注释尺寸 0x69。
- 若 std::map 在 ORIG 为 0x14（_Rb_tree_header=20 字节）而非本工程的 0x18，UserInfo 尺寸会不同。`[Inferred]` —— 需对照 ORIG 构造逐一确认。注意 ServerParameterScript 修复已假定 std::map=0x18 成立（+52 无回归），故此处更可能是打包/字段顺序问题而非 std::map 全局尺寸。

## 6. `m_dailyBadge` 双处歧义 `[Inferred]`

- 存在两处"daily badge"：`SetDailyBadge` 写入基址 0x47044（CUser 内部，+4），而 CUser.h 另有 `short m_dailyBadge[3]` 注释于 +0x8e084。
- 需确认 0x47040 徽章数组属于哪个子对象、为何位于 CNetwork 缓冲区内（或 CNetwork 布局注释与实际不符）。

## 修复建议顺序
1. 先修 `get_growth_power_exp_reward` 语义（独立、明确 bug）。
2. 再查 STExpReward 打包布局（§2/§4），确认后修正，联动 +3 字段。
3. 最后在 0x8d0e4..0x8e07c 区间定位 +4 单点，且逐项核对不破坏已 identical 访问（§1）。
4. 所有修改经 `check_tu_game_orig.sh` 单 TU + `compare_game_full.py` 全量验证无回归后再合并。
