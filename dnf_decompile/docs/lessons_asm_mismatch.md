# 汇编对不齐排查经验（2026-08-15）

## 核心教训

**汇编对不齐时，永远先把「编译器形态」当作最后解释，而不是默认解释。**
编译器（同一工具链族 4.4.x 之间）导致指令序列/帧布局差异的可能性非常小；
大部分看起来"奇怪"的差异，尤其是**帧尺寸、包偏移、字符串内容、常量值、
分支方向**的差异，都是真实的源码语义/结构问题。

## 案例：OnDBReplyGuildSecede 帧差 0x1020

- 表象：ORIG 帧 0x114c，重建 0x216c，差 0x1020（4128 字节）。
- 初判错误：归为"编译器栈分配形态差异"，未深挖。
- 真相：
  1. 我们的 `Packet_DBMW_Query_Msg` 结构体含 `char m_data[0x1001]`（4097 字节），
     ORIG 的该包同样有 m_data——结构体本身没问题；
  2. 但我们的函数里**另外**声明了 `char sql[4097]`，并把 SQL `sprintf` 进独立的
     sql 缓冲，随后 `SendToDB(&query)`——**query.m_data 从未被填充，SQL 实际
     从未发给 DBMW**（真实语义 bug），同时帧多出 0x1001 字节；
  3. ORIG 是 `sprintf(query.m_data, ...)` 直接写进包数据区，没有独立 sql 局部。
- 修复：删独立 sql[4097]、sprintf 直写 query.m_data。帧差 0x1020 → 0
  （两侧均为 0x114c），diff 行数 215 → 179。

## 排查 checklist（按优先级）

1. **帧尺寸差 > 数十字节**：优先怀疑
   - 结构体成员多了大数组/大缓冲（查 Ghidra 伪 C 的 local 声明大小 vs 我们的 struct）；
   - 同一大对象被声明了两次（两个独立大局部并存）；
   - 包结构体尺寸与 ORIG 不符。
2. **包字段偏移差 1 字节 / 数组长度差**：先怀疑 struct 布局（字段顺序、缺失的
   1 字节 pad、数组尺寸 0x128 vs 0x138），而不是"编译器寻址形态"。
3. **字符串/字节内容不同**：直接从 ORIG ELF 的 rodata 读实际字节核对，
   不要假设"我们抄对了"。
4. **分支方向相反（je vs jne）**：先按语义推一遍两边行为，往往是我们写反了。
5. **参数/字段选错（偏移不同但都合法）**：对照 ORIG 读的是哪个偏移。
6. 只有以上全部一致、仅剩**寄存器分配、栈槽编号、lea/add 拆分、nop、
   EH pad 摆放、setcc/test 物化、双重零扩展、浮点指令形态**时，才判编译器形态。

## 判别方法

- 对比 ORIG Ghidra 伪 C 的**局部变量声明列表**与我们的源码局部：
  布局不同 = 结构问题，布局一致才可能是形态问题。
- 大差异（> 30 行 diff 或帧差）必须先做上述 1-5 项排查；
  小差异（个位数指令、同址拆分）才直接考虑编译器形态。
- 判定为"编译器形态"必须给出证据：同一源码在多个可用编译器版本下输出相同、
  或已用多种源码写法尝试仍无法复现 ORIG。
